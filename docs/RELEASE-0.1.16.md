# 0.1.16：修复原生身份查询反复回退造成的降速

## 已确认的问题

第 20 次运行（0.1.15）比第 19 次运行（0.1.14）更慢：

| 指标 | 0.1.14 | 0.1.15 |
|---|---:|---:|
| 全程平均实际复制 | 27.3 文件/秒 | 20.9 文件/秒 |
| 最近约 191 秒实际复制 | 29.2 文件/秒 | 21.2 文件/秒 |
| 根身份平均核验 | 368 ms | 637 ms |

第 20 次 rootNativeQueries 与 rootNativeFallbacks 均为 113756，说明每次尝试原生方式都退回 lstat，额外原生查询开销被重复支付。其他阶段多项耗时反而下降，不能把本次降速笼统归于无线网卡或 NAS 负载。

0.1.15 没有记录根原生回退的具体阶段/错误码，因此不能断言是 FileIdInfo 不支持、权限、共享模式冲突或非链接重解析点。新版补充证据，不把推测当作结论。

## 修复

- 每个目录组新建 RootIdentityReader，首次只允许一个线程探测原生方式。
- 原生方式触发回退后，该目录组后续直接查询 lstat，不再对每个文件重试原生 API。
- 只保存本组的查询方式选择，不缓存文件或目录身份。每次复制前和发布前仍重新查询，并和初始身份比较。
- 首次成功后查询不持有探测锁，仍并行；运行中再发生回退，也切换本组后续查询。已经进入原生查询的其他线程可能各完成一次，在途数量受原线程上限约束。
- 状态不跨目录组/任务持久化。新组重新探测，避免影响其他本地磁盘或不同 NAS。
- 网络错误和身份错误保持原处理，不被转换为成功；不变更删除、链接、时间保留、刷盘与原子发布语义。

## 新指标

- rootNativeBypassed：因本组已选择兼容方式而直接 lstat 的次数。
- rootFallbackOpen / AttributeTag / FileId / Reparse / Unavailable：原生回退阶段计数。
- rootFallbackError1/5/32/50/87/120：已知回退错误码，只有实际出现才记录。
- 诊断样本新增 query=identityBackend、reason=native_root_fallback、stage、winError；该样本的 seconds=0 表示只记录回退原因，不代表原生调用没有耗时。总耗时仍在 identityTargetRootSeconds 中。

错误分类累计保留；路径样本仍服从已有上限，可能被后续样本覆盖。正常预期是本组探测失败后 rootNativeQueries 不再随文件数增长，rootNativeBypassed 持续增加；多个目录组或重试执行会重新探测，因此不是所有场景都要求全任务原生查询恰好为 1。

## 验证

190 项本机回归，187 项通过，3 项原生 Windows 测试跳过。新增并发用例：32 线程、128 次核验，在首次回退场景仅探测一次，128 次真实身份读取仍全部执行；原生成功保持并行；运行中回退不跨目录组污染；网络异常传播；错误阶段与代码可导出。Windows CI 包含这些用例。

修复目的是消除 0.1.15 新增的反复失败开销，预期恢复兼容路径的行为，不承诺超过 0.1.14 的吞吐。该 NAS 的实际速度及回退原因仍需新诊断确认。

## 升级

停止旧进程，解压 0.1.16，沿用原数据库目录和 Python 配置启动。配置协议仍为 5，无数据库迁移。保持性能诊断开启，运行 5–10 分钟后导出，比较 identityTargetRootSeconds/Count、rootNativeQueries、rootNativeBypassed 和最近 copied 增量。既有任务保留，不保证跨进程保存扫描游标。
