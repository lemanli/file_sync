# 0.1.10：按文件发布锁和完整活动状态

## 问题及修复

0.1.9 的网页仅渲染前 4 个活动文件，不能根据这 4 行判断实际并发。后台仍有目录组级全局发布锁，所有文件在锁内串行完成权限复制、时间设置、路径检查及最终替换；网络元数据操作较慢时，即使 32 个线程都在工作，也可能只有每秒几个文件完成。

本版改为按目标文件路径互斥：不同目标并行发布，同一路径及大小写/Unicode 等价路径串行发布。仅锁表增减使用短时内存锁，不在这把锁下执行文件系统操作。路径锁引用数归零立即删除，不随文件总量积累。该锁用于当前目录组进程内的 worker；它不提供跨进程分布式锁，外部竞争仍依靠现有发布检查和原子操作。

权限和时间操作针对各自临时文件并行执行。最终发布前继续检查源目标根目录身份、链接、双向同步指纹和停止状态。保留时间容差、原子替换、跳过已有策略的原子不覆盖发布以及失败时禁止删除的机制。

页面显示全部活动文件（最高 32 个），增加“写入权限和时间”“等待发布锁”“检查路径并发布文件”阶段及阶段停留秒数。仍按原来的 2 秒轮询，不逐文件发请求，不新增逐文件阶段日志写入。活动文件数不是实时正在传输字节的线程数，等待、校验和发布也计入活动状态。

## 验证

151 项 Python 测试通过。新增测试验证独立文件的权限设置和最终替换真正并行、同一目标路径严格互斥、异常后锁表清理以及阶段计时不被字节更新重置。浏览器验证全部 32 个活动状态可见，并保留真实复制、暂停、日志等回归。

延迟模拟基准：本地真实复制 128 个混合文件，文件并发 32、批量 500，仅人为给每文件 copymode 增加 250 毫秒延迟。

| 版本 | 耗时 | 文件/秒 | 峰值活动文件 |
| --- | ---: | ---: | ---: |
| 0.1.9 全局锁 | 32.623 秒 | 3.92 | 32 |
| 0.1.10 文件锁 | 1.065 秒 | 120.19 | 32 |

该测试证明全局锁会放大单文件元数据延迟，以及本次改动消除了这个串行点；不是 Windows SMB/NFS 实测，也不能承诺真实共享盘达到这个速度。原始记录在 `docs/benchmarks/metadata-delay-019.json` 和 `metadata-delay-0110.json`。

复现：`python scripts/benchmark_mixed_copy.py --files 128 --metadata-delay-ms 250`。不传延迟参数即普通本地复制基准；`--backend` 可指定旧版 backend 对照。

## 仍需实机观察

单个巨大目录的快照枚举、AUTO 兼容扫描、网络元数据请求数量、服务端限流、逐文件日志落库及实际磁盘吞吐仍可能成为瓶颈。本次没有取消安全检查，也没有把本地模拟结果当成真实网络提速结果。升级后可根据各文件阶段及停留秒数定位后续瓶颈。

## 升级

正常停止旧程序，解压 0.1.10，沿用固定数据库目录及 Python 配置，运行 `start-standalone.cmd` 后刷新网页。已有任务与日志继续保留。
