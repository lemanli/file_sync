# 0.1.9：混合文件复制调度与暂停调参

## 原因及处理

0.1.8 的复制单位是串行批次。例如 2,000 个文件、每批 500，即使文件并发设为 32，也只有约 4 个批次可供线程执行。新扫描流程还把所有文件视为小文件，未利用扫描结果中的大小识别大文件。CMD 不是这两处问题的原因，升级 Python 不会修复它们。

0.1.9 使用共享文件队列：批次负责入队和汇总，线程共同消费批内文件。每批仍只有一个 Future，待提交批次有界，不为几十万个小文件创建几十万个 Future。已取得大小的大文件独立优先入队，每个大文件由一个线程完整复制；不拆分文件、不预扫描整个树寻找大文件，也不打断已经开始的复制。NAME/TYPE 扫描没有大小时不为分类增加逐文件 stat，仍通过共享队列消除批内串行等待。

暂停后允许修改扫描目录并发、文件并发、入队批量、大文件阈值、限速和重试参数。文件并发在恢复后的文件边界调整，包括已经入队的文件；批量和阈值用于后续入队，扫描并发用于后续目录调度。已开始扫描的目录允许完成。已有源目标、比较方式、覆盖和删除语义继续锁定。

运行界面显示活动文件数量、并发上限、批量以及目录并发是否适用。目录组开始日志记录采用的配置，暂停修改保留原有参数修改审计日志。

## 大量混合文件的使用边界

- COPY_ALL：源文件全部覆盖，不枚举目标；适用于确实希望全部复制的任务。
- COMPARE_METADATA：按目录批量比较大小和时间，适用于时间容差已正确配置的普通单向增量任务。
- AUTO：保留只比较大小、SHA、仅更新、双向等旧语义；本次也改善复制并发，但仍使用兼容扫描，不使用 scanWorkers。不会自动迁移比较方式。
- 单个目录包含几十万个文件时，目录并发不能拆分该目录。仍需先完成该目录快照及名称冲突保护；超过内存阈值使用临时磁盘快照，不建立持久历史索引。本次未消除这段枚举等待。
- 更多线程不保证更快。网络盘还受服务端并发能力、元数据延迟、带宽及安全发布检查限制。日志仍逐文件留存；页面使用已有采样进度，不增加逐文件接口请求。

## 验证及基准

147 项 Python 测试通过；浏览器真实复制及任务操作回归通过；启动 smoke test 通过。新增屏障测试验证同批多文件真实并行、无新增提交时扩容、异常传递，以及 AUTO/COPY_ALL/COMPARE_METADATA 混合大小文件的内容一致性；暂停 API 测试同时修改 scanWorkers、parallelism、batchFiles。

同机本地磁盘，2,000 个文件（每 200 个一个 2 MiB 文件，其余 4 KiB），目录并发 16、文件并发 32、批量 500、大文件阈值 1 MiB，真实复制结果：

| 版本 | 峰值活动文件 | 耗时 | 文件/秒 |
| --- | ---: | ---: | ---: |
| 0.1.8 | 4 | 0.660 秒 | 3031 |
| 0.1.9 | 32 | 0.680 秒 | 2940 |

两次均复制 2,000 个文件、29,122,560 字节。该小规模单次本地测试证明并发限制修复，没有证明速度提升，不能外推为 Windows SMB 性能或几十万文件吞吐。

原始结果：`docs/benchmarks/mixed-018.json`、`mixed-019.json`。
复现：`python scripts/benchmark_mixed_copy.py --files 2000 --parallelism 32 --batch 500`；可通过 `--backend` 指向旧版本 backend 对照。本次未在真实 Windows 网络共享上测量性能。

## 升级

停止旧程序，解压新包，沿用固定数据库目录后运行 `start-standalone.cmd`。保留原 Python 和依赖选项，不要求改用全局 Python 或 venv。已有任务与日志无需重新创建。刷新网页后确认前后台均为 0.1.9。
